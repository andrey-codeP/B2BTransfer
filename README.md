# B2B Transfer API

бэкенд для переводов средств между пользователями. сервис позволяет регистрироваться, логиниться, создавать кошельки и безопасно переводить деньги между ними

писал этот проект для отработки работы с транзакциями, конкурентностью (race conditions) и асинхронной работой с БД на SQLAlchemy 2.0, попробовать архитектуру

## стек
* **язык:** Python 3.14
* **фреймворк:** FastAPI
* **база данных:** PostgreSQL + asyncpg
* **ORM:** SQLAlchemy 2.0 (async)
* **миграции:** Alembic
* **тесты:** Pytest, pytest-asyncio, httpx
* **инфраструктура:** Docker, Docker Compose
* **линтер:** Ruff

## реализованный функционал
* **аутентификация:** JWT-токены (Access), хеширование паролей через Argon2
* **кошельки:** создание, проверка баланса, мягкое удаление
* **переводы:** переводы между пользователями
* **история:** неизменяемый журнал всех движений по кошелькам

## особенности реализации (фичи, которые есть в коде)

**1. слоистая архитектура и Unit of Work**
код разделен на слои: `routers` (HTTP) -> `services` (бизнес-логика) -> `repositories` (работа с БД)
управление транзакциями вынесено в паттерн `UnitOfWork`
это позволяет сервисам работать с несколькими репозиториями в рамках одной транзакции, а не коммитить изменения где попало

**2. наследование исключений и единый формат ошибок**
все кастомные ошибки (например, `InsufficientFundsError`, `UserNotFoundError`) наследуются от базового `AppException`
у каждой ошибки есть свой `status_code` и `error_code`
благодаря глобальному обработчику в `main.py`, клиент всегда получает ошибку в едином формате JSON, а не «сырой» HTML или 500-ку
это упрощает обработку ошибок на фронтенде

**3. защита от Lost Update и Race Condition (главная фича)**
при параллельных переводах стандартный `SELECT` может вернуть устаревший баланс, из-за чего деньги могут потеряться
* **решение:** В сервисе используется блокировка строк `SELECT ... FOR UPDATE`
* **защита от Deadlock:** Чтобы избежать взаимной блокировки при встречных переводах (A -> B и B -> A), кошельки блокируются в строго определенном порядке (сортировка по `id`)

**4. трейдофф с выдачей сессии на каждый запрос (в тестах)**
в тестовой инфраструктуре (`conftest.py`) используется подход, при котором через `dependency_overrides` на каждый HTTP-запрос создается новая сессия
* **зачем:** Это позволяет тестировать параллельные запросы (через `asyncio.gather`), так как `AsyncSession` не потокобезопасна
* **в чем трейдофф:** При высокой степени параллелизма в тестах это может привести к переполнению пула соединений
для интеграционных тестов это осознанный выбор, так как мы получаем 100% изоляцию и возможность проверять блокировки

## тесты
проект покрыт интеграционными тестами (покрытие ~87%). тесты гоняют реальную БД (PostgreSQL в Docker), проверяют как позитивные сценарии, так и ошибки (401, 404, 409, 402)

есть тест на конкурентность: два встречных перевода запускаются одновременно через `asyncio.gather`. Для эмуляции гонки используется `monkeypatch` с искусственной задержкой первого запроса, чтобы проверить, что `FOR UPDATE` реально держит блокировку, а данные в истории записываются корректно

запуск тестов:
```bash
# Поднять тестовую БД
docker compose -f compose.test.yml up -d --wait

# Прогнать тесты
pytest -v

# Погасить БД
docker compose -f compose.test.yml down -v
